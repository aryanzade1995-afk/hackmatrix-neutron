# Hackmatrix — Phase 2 Build Guide: Backend, Real Roles, Real QR, Real AI

## 0. Where this picks up

The frontend (Next.js 14, `frontend/`) is done and verified: multi-patient data model, patient registration with QR generation, find/QR-recovery, and the full 4-step Smart Visit Entry flow (complaint → diagnosis → medicine → review) all work against an in-memory store (`frontend/src/lib/store.tsx`, `useStore()`).

Everything in this guide is about closing the gap between what the pitch claims and what the code actually proves. Right now:

- There is no backend, no database, and no real role separation. `/admin` and `/clinician` are just two routes — nothing stops anyone from typing either URL.
- QR "scanning" is a link that says "Simulate a successful scan." The QR itself is real (generated by `qrcode.react` in `PatientQrPanel.tsx`), but nothing reads it back.
- The AI clinical summary on `/clinician` is a hardcoded paragraph with hardcoded citation badges.
- Data lives only in React state. A page refresh wipes every patient/visit added during a demo.

Build the sections below **in this order**. Each one is a self-contained, demoable unit — commit after each one works, don't chain them into one giant uncommitted change. Section 1 matters most: it's the one technical claim the whole pitch depends on, and it's provable in isolation without touching the frontend at all.

**Non-negotiable constraints, carried over from the frontend and just as binding here:**

- Exactly two roles, ever: clinician and administrator. Do not introduce a third role, service account type, or permission tier anywhere in the database or API, even for internal convenience.
- Never add an endpoint that suggests, ranks, or infers a diagnosis. The medicine-frequency ranking that already exists (`topMedicinesForDiagnosis`) reports statistical fact about what's been prescribed before — it is not, and must never become, a recommendation engine.
- Append-only. There is no `UPDATE` or `DELETE` route for visits anywhere in this plan, and the database grants below deliberately never include `UPDATE`/`DELETE` on the clinician role either — the constraint should be enforced by the database, not just by which routes happen to exist in the API.
- Synthetic data only. Never seed, test, or demo with anything resembling a real patient.

## 1. Real database, real role separation (do this first)

This is the single most convincing thing you can show a judge: not a slide claiming the roles are separated, but Postgres itself refusing a query.

### 1.1 Where to run it

Use a hosted Postgres instance — **Supabase** or **Neon**, both have a free tier — rather than installing Postgres locally. A hosted instance means the demo doesn't depend on your laptop's local service being up, and you can connect to it from anywhere (including a different machine on demo day) with just a connection string.

### 1.2 Schema

Mirror the existing TypeScript shapes in `frontend/src/lib/demo-data.ts` exactly, so a later API layer can return JSON the frontend already knows how to render without any type changes.

```sql
CREATE TABLE patients (
  id            TEXT PRIMARY KEY,              -- "PT-2291"
  name          TEXT NOT NULL,
  dob           DATE NOT NULL,
  gender        TEXT NOT NULL CHECK (gender IN ('Female','Male','Other')),
  phone         TEXT,
  facility      TEXT NOT NULL,
  district      TEXT NOT NULL,
  conditions    TEXT[] NOT NULL DEFAULT '{}',
  allergies     JSONB NOT NULL DEFAULT '[]',    -- array of {label, drugClass, recorded, severity}
  registered_at DATE NOT NULL DEFAULT CURRENT_DATE
);

CREATE TABLE visits (
  id              TEXT PRIMARY KEY,
  patient_id      TEXT NOT NULL REFERENCES patients(id),
  visit_date      DATE NOT NULL,
  display_date    TEXT NOT NULL,                -- pre-formatted, e.g. "12 Aug 2026"
  facility        TEXT NOT NULL,
  diagnosis       TEXT NOT NULL,
  notes           TEXT NOT NULL DEFAULT '',
  prescriptions   JSONB NOT NULL DEFAULT '[]',   -- array of Prescription (see prescribing.ts)
  vitals          JSONB NOT NULL DEFAULT '{}',
  admission       BOOLEAN NOT NULL DEFAULT FALSE,
  chief_complaint TEXT,
  symptom_tags    TEXT[],
  entry_method    TEXT CHECK (entry_method IN ('quick','detailed')),
  supersedes      TEXT REFERENCES visits(id),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_visits_patient ON visits(patient_id);
```

Seed it with the same synthetic patients/visits already in `demo-data.ts` — don't invent new data, just transcribe what's already there so the demo tells one consistent story across frontend and backend.

### 1.3 The two roles

```sql
CREATE ROLE clinician_role LOGIN PASSWORD '<generate one, put it in .env, never commit it>';
CREATE ROLE admin_role     LOGIN PASSWORD '<generate one, put it in .env, never commit it>';

-- Clinician: can read and add, never edit or delete — append-only enforced here,
-- not just by which routes the API happens to expose.
GRANT SELECT, INSERT ON patients, visits TO clinician_role;

-- Admin: explicitly has nothing on the raw tables. This line is redundant with
-- Postgres's default-deny, but write it anyway — it's the line you point at
-- when a judge asks "how do you know the admin role can't see patient records."
REVOKE ALL ON patients, visits FROM admin_role;

-- The only thing the admin role can see: a suppressed aggregate view.
CREATE VIEW district_aggregates AS
SELECT
  district,
  diagnosis,
  COUNT(*) AS case_count
FROM visits v
JOIN patients p ON p.id = v.patient_id
GROUP BY district, diagnosis
HAVING COUNT(*) >= 5;   -- k-anonymity threshold: suppress any cell smaller than this

GRANT SELECT ON district_aggregates TO admin_role;
```

### 1.4 The proof (do this before writing a single line of API code)

```bash
# As the admin role, querying the raw table directly — must fail
psql "postgresql://admin_role:<pw>@<host>/<db>" -c "SELECT * FROM patients;"
# => ERROR: permission denied for table patients

# As the admin role, querying the aggregate view — must succeed
psql "postgresql://admin_role:<pw>@<host>/<db>" -c "SELECT * FROM district_aggregates;"
# => returns rows

# As the clinician role, querying patients directly — must succeed
psql "postgresql://clinician_role:<pw>@<host>/<db>" -c "SELECT * FROM patients LIMIT 1;"
```

Record this terminal session (screen recording or even a screenshot sequence) tonight, while it's fresh — it's your backup if live `psql` on stage is too risky.

**Deliverable for this section:** a `db/schema.sql` file with everything above, and a `db/README.md` that documents the proof (the three commands, what each one demonstrates, and why the separation happens at the database layer rather than in application code). Commit both.

## 2. Minimal FastAPI layer

### 2.1 Structure

```
backend/
  app/
    main.py            # FastAPI app, CORS, router mounting
    db.py              # two SQLAlchemy engines: one authenticated as clinician_role,
                        # one authenticated as admin_role — this is where the
                        # separation actually lives, not in an if-statement
    models.py           # Pydantic schemas mirroring the TS types in demo-data.ts,
                         # formulary.ts and prescribing.ts field-for-field
    routers/
      clinician.py       # every route here uses the clinician engine
      admin.py            # every route here uses the admin engine
  requirements.txt
  .env.example           # DATABASE_URL_CLINICIAN, DATABASE_URL_ADMIN — never commit the real .env
```

The key architectural point: `admin.py`'s routes must be physically incapable of querying `patients`/`visits`, because the database connection they run on has no grant to do so — not because the route handler chooses not to. If someone adds a bug to `admin.py` that tries to `SELECT * FROM patients`, it should fail at the database, loudly, not silently succeed.

### 2.2 Endpoints

Clinician (`/clinician/*`, clinician engine):
- `GET /clinician/patients/{id}` — one patient
- `GET /clinician/patients/search?q=` — case-insensitive match on name/phone/id, same semantics as `findPatientsByQuery` in `clinical.ts`
- `GET /clinician/patients/{id}/visits` — visits for one patient, newest first
- `POST /clinician/patients` — body is a `Patient` minus `id`; server assigns the next `PT-####` id (same scheme as `nextPatientId`), returns the created record
- `POST /clinician/visits` — body is a `Visit` minus `id`/`display_date`; server computes both, inserts, returns the created record. No `PUT`, no `PATCH`, no `DELETE` on this resource, ever — matches the append-only philosophy and the fact that the DB grant wouldn't allow it anyway.

Admin (`/admin/*`, admin engine):
- `GET /admin/aggregates?district=&date_from=&date_to=` — reads only from `district_aggregates`
- `GET /admin/trends` — same view, shaped for the existing `/admin/trends` chart

Enable CORS for `http://localhost:3000` (and whatever origin you'll actually demo from).

### 2.3 Auth

Full login/session auth is out of scope for the time you have left — don't build it. What matters for the pitch is that the *data* separation is real, which section 1 already proves independent of any login screen. For now, it's fine for the existing `/login` page to remain a cosmetic role picker that routes to `/clinician` or `/admin` — just be upfront in the demo that authentication is the one piece still ahead of the database-separation piece, not the other way around.

## 3. Wire the frontend to the real backend

Because `useStore()` was already built as a clean hook (`patients`, `visits`, `addPatient`, `addVisit`), you have a choice, and it's worth making deliberately rather than by default:

**Option A — full swap (do this if the schedule allows).** Rewrite the *inside* of `StoreProvider` in `frontend/src/lib/store.tsx` to fetch from the FastAPI endpoints instead of holding seeded arrays in `useState`, while keeping the exact same return shape. Fetch `patients` and `visits` on mount; `addPatient`/`addVisit` should update local state immediately (so the UI feels exactly as instant as it does now) and fire the `POST` in the background. Because every page only ever calls `useStore()` and never touches the seed arrays directly, **zero changes are needed in any of the five pages that consume it** — `register`, `find`, `visit/new`, the clinician record, and history all keep working unmodified. This is the payoff of having built that abstraction cleanly the first time.

**Option B — demo side-by-side (fall back to this if time runs short).** Leave the frontend exactly as it is, running on the mock store, and demo the database separation from section 1 as its own standalone moment — the `psql` proof, shown live or as the recording — rather than rewiring the UI to depend on it. This is a completely legitimate way to present a Round 1 prototype: the working, polished UI proves UX and completion; the separate database proof proves the security claim. Don't feel obligated to force these into one system if the days aren't there.

Decide which option based on how much of the week is left when you get here — don't let this section block section 1 or 2.

## 4. Real QR scanning

Right now `PatientQrPanel.tsx` generates a real QR encoding just the patient id, but `frontend/src/app/clinician/scan/page.tsx` never reads one back — it only has a "Simulate a successful scan" link. This is the cheapest high-impact fix left: it turns the Register → Scan loop from simulated into actually real, using a QR you can print or show on a phone.

- `npm install html5-qrcode` (or `@yudiel/react-qr-scanner`, either works with a webcam).
- In `scan/page.tsx`, add a camera-reading component. On a successful decode, the value is just the patient id string (that's all `PatientQrPanel` encodes) — look it up with `findPatientById`; if found, `router.push('/clinician?patient=' + id)`; if not found, route to the existing `/clinician/not-found-record?patient=<id>` page, which already exists for exactly this case.
- **Keep the existing "Simulate a successful scan" and "simulate a scan without clinician rights" links visible as a fallback.** A live camera failing on stage — bad lighting, a laptop webcam that won't focus — is a real risk, and having the simulated path still there means one bad camera moment doesn't derail the demo.

## 5. Real AI clinical summary

The summary on `/clinician` (the `Cite`-annotated paragraph) is currently a hardcoded string with hardcoded citation numbers. Replace it with one real model call, but keep it safe to fail.

- Add a Next.js route handler, `frontend/src/app/api/summary/route.ts`, that takes a `patientId`, loads that patient's visits (from the store or backend, whichever is wired up by this point), and calls the Claude API with a prompt that:
  - includes the visit history as structured data (dates, diagnoses, prescriptions, vitals) with an index number per visit
  - instructs the model to write a short clinical summary using *only* facts present in the supplied visits
  - requires every sentence to carry a citation back to a visit index, in a parseable format (e.g. `[[2]]`)
  - explicitly instructs: if a claim can't be traced to a specific visit, drop the sentence rather than include it unsourced — this is the same anti-hallucination framing already written into the UI's subtitle ("Sentences without a source are dropped before display"), so the backend should actually enforce what the UI already promises.
- Parse the citations out of the response and feed them into the existing `<Cite n={}/>` component and the "Sources" badges — both already exist in `clinician/page.tsx`, they just need real data instead of the hardcoded JSX.
- **Fallback:** if the API key is missing, the call errors, or you're demoing somewhere without reliable network, fall back to the existing static mock paragraph rather than showing an error state. A summary feature that occasionally shows honest mock text is fine; a summary feature that visibly breaks mid-demo is not.

This is the highest-effort, highest-"wow" item in this guide — do it after sections 1–4 are solid, not before.
